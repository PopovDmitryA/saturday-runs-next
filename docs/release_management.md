# Релизы и версии сайта

Публичная страница «Обновления» (`/updates`) показывает историю релизов;
номер текущей версии виден в футере. Управление — в админке `/admin/releases`.
Хранилище — таблица `site_releases` (миграция 060).

## Формат версии

`X.Y.Z`, опционально с суффиксом `-fixN`:

- **X** — эпоха: глобальные перемены уровня портального редизайна;
- **Y** — обычный релиз с новыми фичами;
- **Z** — минорные правки и улучшения;
- **-fixN** — в рамках релиза только чинились ошибки (`2.3.0-fix1`, `-fix2`, …).

`2.2.0-fix1` считается НОВЕЕ `2.2.0` (это не prerelease классического семвера).
Сортировка и валидация — `backend/app/services/release_service.py::parse_version`.

## Протокол деплоя (для Claude)

1. **Перед деплоем** — согласовать версию с Дмитрием: показать кандидатов
   (какой разряд растим и почему) и дождаться выбора. Кандидатов считает
   `suggest_next_versions` от последнего релиза в таблице, включая скрытые;
   посмотреть можно так:

   ```bash
   docker compose exec api python scripts/add_release.py --suggest
   ```

2. **После деплоя** — без отдельного согласования внести запись о релизе на
   проде. Запись создаётся СКРЫТОЙ (`is_published=false`):

   ```bash
   docker compose exec api python scripts/add_release.py \
       --version 2.4.0 --title "Короткий заголовок" --body-file /tmp/notes.md
   ```

   Формат текста: абзацы разделяются пустой строкой, пункты — строками `- …`
   (маркдауна на сайте нет, рендер — `renderReleaseBody` в
   `frontend/src/features/portal/PortalUpdatesPage.tsx`).

3. **Дальше — Дмитрий в админке** `/admin/releases`: правит текст/номер/дату
   (карандаш), включает показ на сайте, при желании удаляет релиз из обоймы.

## Правила нумерации

- Пропуски в опубликованных номерах — нормальная практика (решение Дмитрия,
  02.08.2026): скрытый или удалённый релиз просто оставляет дырку, ничего
  не перенумеровываем.
- Следующая версия считается от последней записи в таблице (включая скрытые).
- Номер уникален; правка номера в админке проверяется на конфликт.
